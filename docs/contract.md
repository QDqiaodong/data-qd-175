# Collection loan contract

Each loan has a unique ID, object ID, borrower, start date, and due date. Events have unique IDs, loan ID, type (`dispatch`, `receipt`, `condition`), UTC timestamp, location, and optional condition code. Dispatch/receipt must fall within the loan interval; condition observations may occur at any time. Each loan is `overdue` when the as-of date exceeds due date and no receipt exists; otherwise it is `returned` or `on_loan`. Timeline order is timestamp then event ID. The report surfaces exceptions and does not determine conservation status or insurance value.

The report's `object_custody` projection rebuilds physical custody per object. Only `dispatch` and `receipt` events whose day falls inside their own loan interval participate; condition events are ignored. Participating events are ordered globally per object by timestamp then event ID. A valid dispatch records its loan as active (tagged with that dispatch event ID); a valid receipt removes only its own loan when active. A dispatch while another loan for the same object is still active yields one conflict record per still-active loan, pairing the new dispatch event ID with that loan's earlier dispatch event ID; the per-loan rows are unaffected. Each object represented by a loan has one entry, sorted by object ID, with `active_loan_ids` sorted by loan ID and `conflicts` ordered by the new dispatch (timestamp then event ID) then the earlier dispatch event ID. Empty arrays are used when no loan is active or no conflict occurred.

The report's `condition_hold_violations` projection lists valid dispatches that occur while the dispatched object is under a conservation hold. Hold state is tracked per object across all of that object's loans, independent of any single loan's interval or completion. For each object, its condition and dispatch events are ordered by timestamp then event ID; any condition event may participate regardless of its own loan interval, while only a dispatch whose day falls inside its own loan interval participates. A `condition` event whose `condition_code` is `conservation_hold` makes that event the object's current hold source; `conservation_clear` removes the source; other codes do not affect hold state. A participating dispatch processed while a hold source is set yields a record with `object_id`, `dispatch_event_id`, and the current `hold_event_id`; dispatches never clear a hold. Records are sorted by object ID, dispatch timestamp, then dispatch event ID, and the array is empty when no violation occurs.
